TOTP
====

TOTP is RFC 6238 HOTP with a time-derived moving factor. The class is immutable:
secret, digits, period, and algorithm are fixed at construction.

Construction
------------

.. code-block:: php

   use Infocyph\OTP\TOTP;

   $secret = TOTP::generateSecret();
   $totp = new TOTP(
       secret: $secret,
       digits: 6,
       period: 30,
       algorithm: 'sha1',
   );

Bounds and defaults:

.. list-table::
   :header-rows: 1

   * - Setting
     - Allowed
     - Default
   * - Decoded secret
     - At least 16 bytes
     - 20 generated bytes
   * - Digits
     - 6–9
     - 6
   * - Period
     - 1–86400 seconds
     - 30
   * - Algorithm
     - SHA-1, SHA-256, SHA-512
     - SHA-1

SHA-1, six digits, and 30 seconds provide the broadest authenticator
compatibility. Test non-default profiles against every supported client.

Generation and deterministic time
---------------------------------

.. code-block:: php

   $current = $totp->generate();
   $atTimestamp = $totp->generate(1_700_000_000);

   $currentStep = $totp->getCurrentTimeStep();
   $knownStep = $totp->getTimeStepFromTimestamp(1_700_000_000);
   $secondsLeft = $totp->getRemainingSeconds();

Timestamp arguments are Unix seconds and must be non-negative.
``getRemainingSeconds()`` returns the full period at the exact start of a new
step.

Boolean verification
--------------------

.. code-block:: php

   $valid = $totp->verify(
       otp: $submittedCode,
       timestamp: null,
       pastWindows: 1,
       futureWindows: 1,
   );

This is convenient for calculations that do not require replay state. Total
past and future drift may not exceed 100 steps.

Detailed verification
---------------------

.. code-block:: php

   use Infocyph\OTP\ValueObjects\VerificationWindow;
   use Infocyph\OTP\VerificationReason;

   $result = $totp->verifyWithWindow(
       otp: $submittedCode,
       timestamp: null,
       window: new VerificationWindow(past: 1, future: 1),
   );

   if ($result->matched) {
       $result->matchedTimestep;
       $result->driftOffset;
       $result->verifiedAt;

       if ($result->reason === VerificationReason::Drifted) {
           // Observe client clock drift; do not silently grow the window.
       }
   }

The search order is exact current step, one past, one future, then each larger
distance. ``driftOffset`` is negative for an older code and positive for a future
code.

Replay protection
-----------------

.. code-block:: php

   $result = $totp->verifyWithWindow(
       $submittedCode,
       window: new VerificationWindow(1, 1),
       cache: $stateCache,
       factorId: 'user-42:totp:secret-v3',
   );

The safe CacheLayer authentication-state cache and factor ID are required
together. On a cryptographic match, TOTP atomically stores the matched timestep
with a TTL equal to ``period * (past + future + 1)``. Only a greater timestep
succeeds.

This monotonic rule is stronger than marking only the exact code as used. If a
future step is accepted first, current and past steps are rejected afterward.
Two concurrent submissions of the same step produce exactly one accepted
result when the store is correctly implemented.

Result interpretation
---------------------

* ``Matched``: exact current timestep accepted.
* ``Drifted``: a permitted past/future timestep accepted.
* ``Malformed``: wrong width or non-decimal input.
* ``Mismatch``: shape is valid but no candidate step matched.
* ``Replay``: OTP math matched but monotonic state rejected it.

``matched`` is false for replay. Use the detailed reason for internal audit and
telemetry, but prefer a generic outward authentication failure.

Enrollment
----------

.. code-block:: php

   $payload = $totp->getEnrollmentPayload(
       label: 'alice@example.com',
       issuer: 'Example App',
       additionalParameters: ['tenant' => 'north'],
       withQrSvg: true,
       imageSize: 256,
   );

   $uri = $payload->uri;
   $svg = $payload->qrSvg;

Default algorithm, digits, and period are omitted from the URI. Non-default
values are included automatically. Provisioning content contains the plaintext
secret and must be protected like a password.

Time synchronization
--------------------

Use a trusted server clock with monitored NTP synchronization. A larger
verification window is not a substitute for fixing clock drift. When multiple
application nodes verify codes, they must have aligned clocks and share replay
state.

Enrollment confirmation can use an exact or narrowly drifted verification. Do
not automatically adjust server time or persist a per-user offset based on one
untrusted submission.

RFC example
-----------

.. code-block:: php

   use ParagonIE\ConstantTime\Base32;

   $secret = rtrim(Base32::encodeUpper('12345678901234567890'), '=');
   $totp = new TOTP($secret, digits: 8, period: 30, algorithm: 'sha1');

   assert($totp->generate(59) === '94287082');
   assert($totp->generate(1_234_567_890) === '89005924');

Rotation
--------

Use ``planRotation()`` to validate a replacement and create new enrollment
material. During an overlap, use separate factor IDs for old and new secrets and
verify the new secret first. See :doc:`secret-rotation`.
